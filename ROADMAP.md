# Plugins AD5X — Roadmap и архитектура

> Не новая прошивка и не форк Z-Mod, а UX/integration layer для Flashforge AD5X поверх Z-Mod/Klipper/Moonraker.

## 1. Цель проекта

Flashforge AD5X — недорогая и хорошо модернизируемая CoreXY-платформа, но после перехода на Z-Mod многие возможности остаются доступны в форме макросов, конфигов и разрозненных инструкций. Это даёт большую свободу опытному пользователю, но создаёт высокий порог входа и лишнюю рутину в повседневном использовании.

Цель проекта — приблизить AD5X к уровню удобства закрытых экосистем наподобие Bambu Lab, **не жертвуя открытостью, модульностью и доступом к низкоуровневым настройкам**.

Главный UX-критерий:

> **90% повседневных действий должны выполняться без Wiki, SSH, консоли и знания названий макросов.**

Обычный пользователь должен видеть понятные сценарии вроде:

- «Я поменял сопло»;
- «Установил боковой вентилятор»;
- «Поставил новую катушку в IFS»;
- «Плохой первый слой»;
- «Подготовить принтер к ABS/ASA»;
- «Почему принтер не стартует?»;
- «Собрать диагностику».

Под капотом при этом могут использоваться существующие механизмы Z-Mod, Klipper и Moonraker.

---

## 2. Что проектом НЕ является

### Не форк Z-Mod

Z-Mod остаётся фундаментом системы и должен обновляться из оригинального репозитория автора без нашей прослойки и без необходимости поддерживать собственную копию его кода.

Мы не хотим:

- переписывать уже работающие механизмы Z-Mod;
- разносить локальные патчи по его отслеживаемым файлам;
- создавать параллельную несовместимую прошивку;
- переносить на себя сопровождение Klipper/Moonraker/Z-Mod целиком.

Наша задача — **интегрировать, автоматизировать и сделать существующие возможности понятными**.

### Не тяжёлый сервер на MIPS

AD5X имеет ограниченные вычислительные ресурсы. Поэтому проект не должен превращать принтер в платформу для тяжёлых сервисов.

Не планируется размещать на принтере:

- AI/computer vision для постоянного анализа камеры;
- тяжёлые базы временных рядов;
- встроенный слайсер;
- постоянное перекодирование видео;
- тяжёлую обработку G-code;
- сложные фоновые web-сервисы, если задачу можно решить через UI/macros/events.

## 3. Базовые принципы архитектуры

### 3.1. Z-Mod — upstream и источник инженерной логики

Используем возможности Z-Mod максимально штатно. Наш код должен по возможности жить в пользовательских overlay/config/plugin-слоях и переживать обновления upstream.

### 3.2. UI first, daemon last

Каждый компонент относится к одному из классов:

| Класс | Подход | Политика |
|---|---|---|
| **A — UI / Macro only** | UI, Moonraker API, существующие макросы | предпочтительный вариант |
| **B — Lightweight backend logic** | лёгкая event-driven логика, редкий polling | допускается при необходимости |
| **C — Heavy service** | тяжёлый CPU/I/O, постоянная обработка | на AD5X не устанавливаем; только sidecar |

Принцип фоновой работы:

> **Плагин большую часть времени спит, просыпается по событию, делает минимум работы и снова спит.**

### 3.3. Один backend — несколько frontend

Бизнес-логика и состояние не должны дублироваться отдельно для Fluidd, Mainsail и экранов.

Предпочтительная схема:

```text
                    ┌──────────── Fluidd
                    ├──────────── Mainsail
Z-Mod / Moonraker   ├──────────── HelixScreen
+ Plugins AD5X      ├──────────── Guppy
                    └──────────── KlipperScreen
```

Frontend — это представление общих возможностей, а не отдельная реализация каждой функции.

### 3.4. Простота не отменяет Advanced

Для обычного пользователя показываем безопасный сценарий и понятное состояние.

Продвинутый пользователь всегда должен иметь возможность:

- увидеть реальные параметры;
- открыть конфиг;
- посмотреть вызванные макросы/API;
- вручную переопределить автоматику;
- отключить наш слой и вернуться к обычному Z-Mod.

### 3.5. Fail-safe и rollback

Любая функция проекта должна проектироваться так, чтобы её поломка **не превращала принтер в кирпич и не создавала опасного движения**.

Требования:

- резервная копия перед изменением конфигов;
- транзакционная установка там, где это возможно;
- проверка конфигурации до рестарта;
- понятный uninstall;
- rollback на предыдущую рабочую конфигурацию;
- базовый Z-Mod должен оставаться доступным после удаления нашей надстройки;
- safety-critical автоматизация должна отказываться от действия при неоднозначности, а не угадывать.

## 4. Стратегия веток

### `main`

Стабильная публичная ветка.

В неё попадает функциональность, которая:

- полезна владельцу обычного AD5X + Z-Mod;
- не требует конкретной личной конфигурации принтера;
- корректно работает при отсутствии опционального железа;
- имеет понятный install/uninstall;
- прошла реальную проверку на принтере;
- не ломает штатные обновления Z-Mod.

### `dev`

Экспериментальная ветка и личная лаборатория.

Здесь допускаются:

- конкретная личная конфигурация железа;
- Flook32;
- Air Manager;
- экспериментальные камеры;
- нестандартные хотэнды;
- новые UI-концепции;
- функции без полного backward compatibility;
- временные debug-инструменты.

Важно: `dev` не должен становиться отдельным продуктом по архитектуре. Экспериментальные функции следует делать модулями/feature flags, чтобы после стабилизации их можно было перенести в `main` без переписывания.

### Критерий переноса `dev → main`

Функция считается кандидатом на перенос, если:

1. её API/конфигурация перестали постоянно меняться;
2. она пережила обновления Z-Mod;
3. установка и удаление воспроизводимы;
4. отсутствие соответствующего железа не ломает систему;
5. пользовательский сценарий понятен без чтения исходников;
6. ошибка функции не мешает базовой печати;
7. для safety-critical функции отрицательные сценарии и реальные hardware gates приняты отдельно.

## 5. Frontend strategy

### Fluidd

Основной первый frontend, поскольку Z-Mod уже поддерживает собственный fork Fluidd.

Цепочка обновлений предполагается такой:

```text
fluidd-core/fluidd
        ↓
ghzserg/fluidd
        ↓
наш fork Fluidd
```

Наши изменения должны быть максимально локализованы: отдельные страницы, компоненты, store/API-модули и минимальное число точек интеграции в upstream-код.

Цель — не размазать AD5X-специфичный код по всему Fluidd, чтобы обновления upstream не превращались в постоянный merge-conflict hell.

### Mainsail

Второй web frontend после стабилизации общего API. Пользователь должен иметь возможность выбрать UI без потери основных возможностей проекта.

### HelixScreen / Guppy / KlipperScreen

Экранные frontends используют тот же backend/API и отображают наиболее полезные операции непосредственно на принтере.

KlipperScreen parity не начинается как продуктовый dependency до отдельной успешной AD5X runtime/platform acceptance.

# 6. Roadmap

## Phase 0 — Platform Foundation

**Приоритет: критический.**

До дальнейшего роста количества плагинов необходимо определить единый каркас.

### Задачи

- единая структура модулей;
- manifests для hardware/software modules;
- единый способ хранения состояния;
- общий API для frontend;
- единая система install/update/uninstall/rollback;
- feature flags;
- обнаружение доступного железа там, где это возможно;
- логирование без постоянного тяжёлого I/O;
- версия и compatibility matrix;
- подготовка fork Fluidd;
- безопасный backend deployment lifecycle;
- документация для разработчика модуля.

### Результат

Новые функции перестают быть набором несвязанных shell-скриптов и конфигов и получают единый жизненный цикл.

## Phase 1 — Hardware / Mods Manager

**Приоритет: очень высокий.**

Центральная страница физической конфигурации AD5X.

### Проблема

Сегодня даже простая модернизация вроде установки бокового PLA/AUX fan выглядит так:

```text
распечатать стойку/дакт
→ установить вентилятор
→ подключить к плате
→ найти чей-то GitHub
→ найти нужный конфиг
→ понять, куда его вставить
→ проверить pin/config
→ перезапустить Klipper
```

Нормальный UX должен выглядеть так:

```text
Side / AUX Fan
[✓] Установлен
```

После включения модуль сам применяет известную конфигурацию, проверяет её и добавляет управление в UI.

### Планируемые hardware modules

- Side / AUX / PLA Fan;
- Enclosure;
- IFS;
- Camera 1 / Camera 2;
- Chamber heater;
- Recirculation;
- Exhaust;
- тип хотэнда/сопла как capability/config identity, но не как владелец скрытого Z-offset profile;
- дополнительные датчики;
- позднее — другие community hardware mods.

### Manifest модуля должен описывать

- имя и версию;
- совместимые модели/ревизии;
- зависимости;
- необходимые Klipper/Moonraker include;
- требуемые GPIO/устройства;
- способ проверки доступности;
- UI capabilities;
- install/uninstall hooks;
- конфликты с другими модулями.

### UX

У обычного пользователя — переключатель и краткое состояние.

В `Advanced`:

- какой конфиг будет добавлен;
- какой pin/device используется;
- что именно изменилось;
- тест устройства;
- ручные overrides.

## Phase 2 — IFS Manager 1.0

**Приоритет: очень высокий.**

IFS должен перестать быть набором макросов и примитивным соответствием `тип + один RGB-цвет`.

### Основная сущность — конкретная катушка

Карточка катушки:

- производитель;
- линейка/серия;
- материал;
- модификация/композит;
- основной цвет;
- несколько цветов;
- эффект: matte / silk / glitter / translucent и т. п.;
- тип окраски: dual / tri-color / radial / coextrusion / rainbow;
- остаток;
- профиль температур;
- профиль печати;
- идентификатор Spoolman;
- физический слот IFS.

### Главный принцип выбора

**Цвет не должен быть единственным идентификатором материала.**

Два близких оттенка не должны автоматически заставлять принтер выбирать случайную катушку.

Предпочтительная логика:

1. точное назначение конкретной spool/slot;
2. материал и профиль;
3. дополнительные свойства;
4. цвет — как визуальный и вспомогательный признак;
5. если соответствие неоднозначно — запрос подтверждения пользователя.

### UX

```text
IFS

Slot 1  eSUN PLA+ Black        612 g
Slot 2  eSUN PLA Silk Dual     843 g
Slot 3  — пусто —
Slot 4  TPU 95A Black          420 g
```

Без необходимости помнить `COLOR`, переменные и внутренние команды.

## Phase 3 — Z Calibration Subsystem / Calibration Center v2

**Приоритет: очень высокий / safety-critical.**

Текущий активный design/work item: **issue #13 — CALIBRATION-SUBSYSTEM-002**.

Старый profile-based CALIBRATION-CENTER-001 (#5 / PR #6) закрыт без merge и остаётся только исследовательской историей.

### Цель

Сделать замену хотэнда/сопла/пластины и обычный старт печати понятным и безопасным сценарием без ручного знания внутренностей Z-Mod.

```text
пользователь запускает калибровку/печать
→ система готовит probe
→ безопасно устанавливает текущий nozzle↔bed reference
→ валидирует серию измерений
→ применяет выбранную bed-mesh policy
→ формирует обычный Klipper effective Z-offset
→ объясняет результат в UI и журнале
→ печатает
```

### Модель Z-offset

Внутренне различаются источники:

```text
Auto-Z alignment
+ persistent user Z trim
+ slicer/job Z offset
+ live babystepping
────────────────────────
= effective Klipper gcode_offset
```

Наружу остаётся стандартная Klipper-семантика. Никакой второй скрытой продуктовой системы координат.

### Хотэнды/сопла

Нормальные persistent Z profiles под каждую инструментальную сборку не требуются.

После замены система заново измеряет nozzle↔bed reference. Большой подтверждённый delta переводит workflow в `hardware_change_suspected` / full calibration, а не превращается в огромный автоматический offset.

### Bed mesh перед печатью

Пользователь получает три режима:

```text
saved
saved+check   ← рекомендуемый
runtime       ← свежая карта перед этой печатью, по духу как stock AD5X
```

Runtime map не затирает permanent/default mesh автоматически.

### First-layer verifier

Тестовый первый слой **опционален** и запускается по желанию/рекомендации пользователя, а не перед каждой печатью.

Основные измерения должны быть достаточны для геометрической калибровки при прохождении safety/metrology gates.

First-layer test проверяет уже полный технологический процесс: extrusion, plate, material, temperature, flow и желаемый squish. Он рекомендуется после первого включения, крупной смены hardware/plate, большого подтверждённого reference change, настройки persistent user trim или по явному запросу.

### Plate protection

Обязательные свойства:

- bounded Z search;
- conservative initial acquisition;
- slow final approach;
- repeated reference validation;
- outlier/drift/spread/plausibility gates;
- early/no-trigger fail-closed;
- large unexpected delta не применяется молча;
- cancel/failure не меняет persistent user trim и saved mesh;
- abort/retract;
- H7 вторичен до отдельного доказательства latency/stop-distance;
- thresholds только после source/hardware evidence + margin.

### Diagnostics

Отдельный bounded structured event log должен позволять понять:

- что измерено;
- какие offset components были активны;
- какая mesh policy использовалась;
- что применено;
- почему решение принято/отклонено;
- какая защита сработала.

### UI

Обычный экран показывает:

```text
Z calibration      Ready
Bed mesh           Saved + checked
Current Z-offset   +0.006 mm
Auto correction    +0.036 mm
User trim          -0.030 mm
Job offset          0.000 mm

[Check Z]
[Build bed mesh]
[Full calibration]
[Test first layer]
```

Advanced раскрывает raw probe/reference/mesh/offset/log state.

### Test policy

`docs/Z_CALIBRATION_TEST_PLAN_V2.md` является обязательным release contract.

Safety-critical paths сначала доказываются в pure/fake tests, затем контролируемо на реальном принтере.

## Phase 4 — Print Preflight / Safe Start

**Приоритет: высокий.**

Preflight — guard перед штатным запуском печати, а **не собственный print engine**.

### Проверки

- Klipper Ready;
- MCU Ready;
- IFS Ready;
- выбранные материалы реально установлены;
- hardware/capability state;
- Z Calibration readiness и выбранная bed-mesh policy;
- G-code metadata обработаны;
- slicer/job Z-offset распознан и отображён;
- достаточно свободного места;
- нет критических ошибок системы.

### UX

```text
✓ Klipper
✓ MCU
✓ IFS
✓ Filament assignment
✓ Z calibration
✓ G-code metadata

⚠ Slot 2: файл ожидает PLA Blue,
  установлено PLA Silk Dual Blue/Green

[Подтвердить и печатать]
```

После проверки вызывается штатный механизм печати Z-Mod.

## Phase 5 — Camera Manager

**Приоритет: средне-высокий.**

### Задачи

- камеры определяются по USB identity/name, а не только `/dev/videoN`;
- Camera 1 и Camera 2 имеют независимый lifecycle;
- отсутствие второй камеры не влияет на основную;
- resolution/FPS/format/port в UI;
- ручной restart отдельной камеры;
- восстановление после restart/reconnect;
- лёгкий health check;
- интеграция с Notify/Timelapse без тяжёлого video processing.

Важно: управление камерами должно стать hardware module + UI, а не набором ручных shell-правок.

## Phase 6 — Maintenance, Diagnostics, System Health

Эти компоненты объединены общей задачей:

> **Принтер должен объяснять своё состояние человеку.**

### Maintenance Assistant

Событийные счётчики и обслуживание:

- часы печати;
- смазка направляющих;
- проверка ремней;
- обслуживание сопла;
- PTFE;
- IFS cutter / 4-in-1 / gears;
- фильтры;
- вентиляторы;
- пользовательские интервалы.

### Diagnostics

Одна кнопка «Собрать диагностику».

Пакет может включать:

- версии firmware/Z-Mod/plugins;
- логи Klipper/Moonraker;
- Plugins AD5X structured event logs;
- MCU state;
- CPU/RAM;
- USB mapping;
- cameras;
- IFS state;
- Wi-Fi metrics;
- relevant config.

Перед экспортом удаляются секреты, пароли и API keys.

### Lightweight System Health

Не полноценный мониторинг-сервер, а дешёвые показатели с человеческой интерпретацией:

```text
Система      🟢 Норма
Печать       🟢 Стабильна
MCU          🟢 Норма
Wi-Fi        🟠 Слабый сигнал
Память       🟢 Норма
```

Во время печати — никакого агрессивного автоматического restart/recovery без явной необходимости.

## Phase 7 — Advanced Hardware Integrations

Сначала развивается в `dev`, затем зрелые и универсальные компоненты могут переходить в `main`.

### Планируемые направления

- Flook32 chamber heater integration;
- Air Manager;
- recirculation;
- filtered exhaust;
- расширенное управление AUX fan;
- enclosure profiles;
- несколько камер;
- нестандартные хотэнды;
- дополнительные датчики температуры/давления/оборотов.

### Пример высокоуровневого сценария

```text
[Подготовить AD5X к ABS]

→ проверить chamber heater
→ включить рециркуляцию
→ выставить профиль AUX

→ после печати выполнить purge/exhaust sequence
```

Конкретные устройства при этом остаются независимыми подсистемами со своей safety-логикой.

## Phase 8 — Frontend parity

После стабилизации общего backend API конкретного модуля:

1. Fluidd — основной первый frontend;
2. Mainsail — функциональный parity основных модулей;
3. HelixScreen — ключевые сценарии непосредственно на принтере;
4. Guppy — адаптер ключевых сценариев;
5. KlipperScreen — после отдельной AD5X runtime/platform acceptance.

Не требуется делать интерфейсы пиксель-в-пиксель одинаковыми. Требуется единая бизнес-логика, compatible state/actions и одинаковая safety semantics.

Плохо:

```text
Z calibration: Ready
Current Z-offset: +0.006 mm
Auto correction: +0.036 mm
User trim: -0.030 mm
```

## 7.2. Показывать проблему и следующее действие

Не только:

```text
probe error / calibration invalid / hardware changed
```

А:

```text
Высота поверхности значительно отличается от сохранённой карты.
Измерение повторено и изменение подтверждено.

[Полная калибровка]
[Построить новую карту]
[Отмена]
```

## 7.3. Не угадывать там, где ошибка дорога

Если система не уверена в катушке, hardware state, Z-reference или safety condition — она должна попросить подтверждение/отказаться от автоматического действия, а не молча выбрать наиболее похожий вариант.

## 7.4. Progressive disclosure

По умолчанию — простой интерфейс.

`Advanced` открывает детали, но они не должны быть обязательными для обычной эксплуатации.

## 7.5. Любая автоматика имеет override там, где это безопасно

Пользователь может вручную:

- выбрать катушку;
- изменить fan speed;
- отключить автоматический сценарий;
- открыть настоящий config;
- вызвать макрос;
- использовать стандартный Klipper Z-adjust;
- продолжить после некритичного предупреждения, если safety policy допускает это.

Safety-critical lower bounds/plate-protection не являются удобством, которое можно случайно отключить обычным UI toggle.

# 8. Политика обновлений и upstream

## Z-Mod

Не форкаем. Сохраняем штатный upstream и максимально используем пользовательские конфиги/overlays/plugins.

## Fluidd/Mainsail/screens

Допускаются собственные frontend forks/adapters для нативной интеграции UI.

Требования:

- явное указание upstream и авторства;
- сохранение лицензий;
- минимизация изменений upstream-файлов;
- собственные модули по возможности изолированы;
- upstream sync сначала проходит через отдельную sync/test ветку;
- автоматический merge не публикуется в stable без сборки и проверки;
- safety/business logic не копируется отдельно в каждый frontend.

## Release policy

`main` должен быть скучным и предсказуемым.

Эксперименты происходят в `dev`/feature branches и только после стабилизации становятся публичным функционалом.

Safety-critical Z Calibration не переносится в stable до полного `docs/Z_CALIBRATION_TEST_PLAN_V2.md` acceptance и explicit owner acceptance.

# 9. Ближайший порядок работ

Архитектурный порядок проекта сохраняется, но owner-approved CALIBRATION-SUBSYSTEM-002 может идти параллельно на отдельной feature branch, используя уже принятый backend foundation.

Текущий порядок:

1. **Platform Foundation** — backend/API/lifecycle/rollback/frontend integration seams;
2. **CALIBRATION-SUBSYSTEM-002** — сначала core model + safety tests + backend, затем Fluidd UI и controlled hardware acceptance;
3. **Hardware / Mods Manager** — Side/AUX/PLA Fan как минимальный hardware module;
4. **IFS Manager 1.0** — spool/slot/material model;
5. **Print Preflight / Safe Start** — использует уже стабилизированный Z Calibration readiness;
6. **Camera Manager** — перенести текущую двухкамерную интеграцию в общую архитектуру;
7. **Maintenance + Diagnostics + System Health**;
8. **Advanced hardware modules** в `dev`;
9. **Mainsail / HelixScreen / Guppy / KlipperScreen parity** по стабилизированным API.

Это порядок архитектурных приоритетов, а не запрет на контролируемую параллельную работу. Уже существующие рабочие компоненты продолжают поддерживаться.

# 10. Критерий успеха проекта

Проект можно считать удачным, если новый владелец AD5X с Z-Mod способен:

- установить поддерживаемый hardware mod без ручного копирования чужих конфигов;
- поменять сопло/хотэнд и восстановить корректную геометрию/первый слой через безопасную автоматическую калибровку без выбора скрытого Z-профиля;
- при желании строить свежую карту стола перед печатью как на stock, либо использовать сохранённую с проверкой;
- видеть, из чего сложился текущий Z-offset, включая slicer/job/live corrections;
- загрузить/назначить материалы IFS без понимания внутренних макросов;
- понять, почему печать не стартует;
- выполнить базовое обслуживание;
- собрать диагностику;
- обновить систему;

— и при этом **ни разу не открыть SSH или Wiki**, если он сам этого не хочет.

А опытный пользователь при этом не теряет доступа к Klipper, Moonraker, макросам и конфигам.

Это и есть основная идея Plugins AD5X: **Bambu-подобный уровень повседневного UX поверх открытой, модульной и модернизируемой платформы.**
